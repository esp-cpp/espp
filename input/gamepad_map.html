Gamepad Map APIs#

Gamepad Map#

The gamepad_map component remaps a gamepad’s buttons and axes: button to button, analog to digital (a stick direction or trigger past a threshold), digital to analog (a button driving an axis) and analog to analog (swap, invert, scale), plus radial stick dead zones. GamepadState names buttons by position (south / east / west / north) so a map means the same thing for Xbox, Nintendo and PlayStation controllers. GamepadProfiles keeps a default map and one map per controller type (vendor / product ID) in a file, stored with PersistentData. to_gamepad_state() converts the runtime HID decoder’s hid_rp::GamepadReport.

Each profile, and the default map, also carries RumbleOptions: how a host’s rumble plays on that controller type. Rumble can be turned off (the device sends a stop instead), scaled from 0 to 200 % (above 100 % each motor saturates at full on its own), and the strong and weak motors can trade places (the trigger motors are never swapped). A profile created from the console, or with GamepadProfiles::set_profile_map(), starts with the default map’s rumble options. GamepadProfiles::rumble_for() looks them up next to map_for(). The library never applies them by itself: the application calls RumbleOptions::apply() once, on the host’s raw request, just before encoding it for the controller. The options are edited from the console together with the map.

GamepadMapService serves a GamepadProfiles store over any framed byte stream (dispatcher module 11, protocol espp.gamepad_map v1), so the hosted Gamepad Map Console web app can edit the maps and their rumble options over WebUSB / Web Serial and show the controller’s input before and after mapping, live.

Code examples for the Gamepad Map API are provided in the gamepad_map example (decode, map, profiles) and webapp_example (the service over USB with the web console) folders.

class GamepadMapService : public espp::BaseComponent#

Serves a GamepadProfiles store over any framed byte stream so a host (the hosted gamepad map web console) can view and edit the maps and watch a controller’s input live (dispatcher module 11 by default; see Config::module).

The application tells the service which controller is connected (set_controller() / clear_controller()) and hands it every input it maps (publish_input(), raw and mapped). The service answers GET_INFO / GET_MAP / LIST_PROFILES from the store, applies SET_MAP / ERASE_PROFILE / RESET_ALL to it (every map is validated, every change saved), and while a host has the stream on, sends the latest input as INPUT events every period. The stream stops by itself when the host does not renew it within Config::stream_lease, so a closed browser tab does not leave it running.

When a change affects the map of the connected controller (its profile, or the default map it falls back to), the service calls Config::on_active_map_changed with the new map: the application swaps the map it applies. Likewise, when a change gives the connected controller different rumble options (see RumbleOptions), the service calls Config::on_active_rumble_changed with them: the application applies the new options to the rumble it forwards. With Config::on_test_rumble set, a host can also try rumble options before saving them (TEST_RUMBLE): the application plays a short test pattern through them on the connected controller. publish_input() only copies the state under a lock (no I/O), so it can be called for every report.

Several services (one per transport) may share one GamepadProfiles store; tell each about the controller and feed each the input. Their changes and notifications are serialized on the store’s change_mutex(), so the last notification always carries the map (and rumble options) the store holds.

**Threading**: an internal mutex covers the parser, the controller state and the stream task; every outbound frame is serialized on a send mutex held across `send`, so frames never interleave. set_controller(), clear_controller() and publish_input() never send (an INFO for a controller change goes out from the stream task), so they are safe to call from a radio / host task. `send`, `on_active_map_changed` and `on_active_rumble_changed` must not re-enter this object (nor change the store).

GamepadMapService Example#

  // One GamepadMapService per transport, both serving the one profile store.
  // When the console changes the map the connected controller uses, the
  // service hands it over: swap the map the input path applies.
  auto on_map_changed = [&](const espp::GamepadMap &map) {
    std::lock_guard<std::mutex> lock(map_mutex);
    active_map = map;
    logger.info("Map changed from the console: {} rule(s)", map.rules.size());
  };
  // Likewise when the console changes its rumble options: a real application
  // passes them to its rumble sender, which re-applies them to the host's last
  // raw request, so the change is felt at once.
  auto on_rumble_changed = [&](const espp::RumbleOptions &rumble) {
    std::lock_guard<std::mutex> lock(map_mutex);
    active_rumble = rumble;
    logger.info("Rumble options changed from the console: off={} strength={}% swap={}",
                rumble.is_off(), rumble.strength_percent, rumble.swaps_motors());
  };
  // The console's rumble Test: a real application plays a short pattern on the
  // controller through these (unsaved) options (start it and return; false with
  // a reason when it cannot, e.g. no controller). The demo controller has no
  // motors, so this just logs what it would play.
  auto on_test_rumble = [&](const espp::RumbleOptions &rumble, std::string &) {
    logger.info("Rumble test requested: off={} strength={}% swap={}", rumble.is_off(),
                rumble.strength_percent, rumble.swaps_motors());
    return true;
  };
  espp::GamepadMapService vendor_map({.send = vendor_send,
                                      .profiles = &profiles,
                                      .on_active_map_changed = on_map_changed,
                                      .on_active_rumble_changed = on_rumble_changed,
                                      .on_test_rumble = on_test_rumble,
                                      .task_config = {.name = "gpmap_v", .stack_size_bytes = 4096},
                                      .log_level = espp::Logger::Verbosity::INFO});
  espp::GamepadMapService cdc_map({.send = cdc_send,
                                   .profiles = &profiles,
                                   .on_active_map_changed = on_map_changed,
                                   .on_active_rumble_changed = on_rumble_changed,
                                   .on_test_rumble = on_test_rumble,
                                   .task_config = {.name = "gpmap_c", .stack_size_bytes = 4096},
                                   .log_level = espp::Logger::Verbosity::INFO});

  // A controller connected: tell every service first, then start from its map
  // and rumble options (all under the same mutex as the callbacks above, which
  // may run on a dispatcher thread), so a change through either service lands
  // before the lookup or notifies.
  {
    std::lock_guard<std::mutex> lock(map_mutex);
    vendor_map.set_controller(demo_vid, demo_pid, demo_name);
    cdc_map.set_controller(demo_vid, demo_pid, demo_name);
    active_map = vendor_map.active_map();
    active_rumble = vendor_map.active_rumble();
  }

class GamepadProfiles : public espp::BaseComponent#

Per-controller-type gamepad maps and rumble options, stored in a file with PersistentData.

Holds a default map and default RumbleOptions plus one GamepadProfile (map and rumble options) per controller type, and saves every change atomically (see PersistentData) to a file on a mounted filesystem (LittleFS, SPIFFS, SD). Look a controller up when it connects (map_for(), rumble_for()) and keep what is returned for its reports / rumble; the lookups copy and are not meant for every report.

Every map that comes in is checked with GamepadMap::valid(), and every RumbleOptions with RumbleOptions::valid(), so nothing invalid is ever saved. From a file, an invalid rule is dropped (the rest of its map kept), unknown rumble flag bits are cleared and a rumble strength over 200 % is clamped, and a profile no controller can match, a duplicate or one over the limit is dropped, each with a warning. A file that cannot be read (corrupt, or written by a newer firmware) is renamed to `<file>.unreadable` and the store starts from the defaults, so the next change does not overwrite what may still be recoverable (see load_error()).

The file is schema version 2 (rumble options). A version 1 file (maps only) loads, migrated in memory with neutral rumble options everywhere (Config::default_rumble does not apply to it), and stays version 1 on flash until the first change writes version 2. After that, older firmware cannot read the file: it sets it aside as `<file>.unreadable` and starts from its defaults.

Thread-safe.

Gamepad Profiles Example#

    // The default map is used for controllers without a profile; the file is
    // written on the first change.
    espp::GamepadMap default_map;
    default_map.invert(A::LeftY).invert(A::RightY); // up-positive sticks for this host
    espp::GamepadProfiles profiles({
        .file_path = path,
        .default_map = default_map,
        .log_level = espp::Logger::Verbosity::INFO,
    });

    // A profile for one controller type (vendor / product ID; from the BLE
    // Device Information PnP ID, or the USB device descriptor).
    espp::GamepadMap bsp_d8 = default_map;
    bsp_d8.swap(B::South, B::East);
    if (!profiles.set_profile({.vid = 0x1949, .pid = 0x0402, .name = "BSP-D8", .map = bsp_d8}, ec))
      logger.error("Could not save the profile: {}", ec.message());

    // When a controller connects, look its map up once and keep it.
    const espp::GamepadMap active = profiles.map_for(0x1949, 0x0402, "BSP-D8");
    logger.info("BSP-D8 map: {} rule(s); default map: {} rule(s)", active.rules.size(),
                profiles.default_map().rules.size());

inline bool set_profile(const GamepadProfile &entry, std::error_code &ec)#

Add a profile, or replace the one for the same controller, and save.

Replaces the whole profile, rumble included: `{.vid, .pid, .name, .map}` resets its rumble to neutral; use set_profile_map() to change only the map.

Parameters:

  • entry – The profile (its map and rumble options must be valid(); with VID and PID 0 it needs a name; a name is stored cut to MAX_NAME_LENGTH).

  • ec – Set on failure: std::errc::invalid_argument for an invalid profile, std::errc::no_buffer_space when the store is full, else the save error.

Returns:

true if saved.

inline bool set_profile_map(uint16_t vid, uint16_t pid, const std::string &name, const GamepadMap &map, std::error_code &ec)#

Set a controller’s map, keeping its rumble options, and save.

Replaces only the map (and the stored name, as set_profile() does) of the controller’s profile. A controller without a profile gets a new one with this map and the default rumble options.

Parameters:

  • vid – The controller’s vendor ID.

  • pid – The controller’s product ID.

  • name – The controller’s name (needed with VID and PID 0; stored cut to MAX_NAME_LENGTH).

  • map – The map (must be valid()).

  • ec – Set on failure: std::errc::invalid_argument for an invalid map or a missing key, std::errc::no_buffer_space when the store is full, else the save error.

Returns:

true if saved.
